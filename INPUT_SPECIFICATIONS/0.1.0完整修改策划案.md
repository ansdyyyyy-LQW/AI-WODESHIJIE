# Maid AI 0.1.0 完整修改策划案（审查修正版）

> **适用工程**：`MaidAI-0.1.0-CompleteSource`  
> **依据策划**：`MaidAI_全新开发_完整技术版_总览修正版`  
> **核验环境目标**：Minecraft Java 1.20.1 / Forge 47.x / Java 17 / Touhou Little Maid 1.5.3  
> **文档性质**：针对当前已经制作出的 0.1.0 工程进行定向修复、补齐和最终验收；**禁止推倒重做**。  
> **核心目标**：把当前“底层骨架已经成立，但大量能力只有类/表/页面壳而没有运行闭环”的版本，修成真正满足原策划案 DoD 的可运行产品。

# 0. 当前版本总判断

当前 0.1.0 **不是空壳工程**。以下底层方向已经基本正确，应保留：

- Touhou Little Maid `EntityMaid` 作为唯一真实身体；
- `@LittleMaidExtension` + `MaidAutonomousTask`；
- `MotionArbiter` 单一移动所有权；
- Java WebSocket Client → Python Agent WebSocket Server；
- 网络线程与 Minecraft Server Thread 隔离；
- Observation / Action Engine 基础；
- `move_to / break_block / place_block / craft / smelt / combat` 等基础 Action 已有真实代码；
- Agent Core 已有 Goal / Plan / Step / Postcondition 框架；
- OpenAI-compatible Provider、模型名原样透传、CredentialStore；
- Runtime / R&D Token Ledger 已分表；
- R&D Handoff、Control Center、PyInstaller 和诊断已有基础框架。

但当前工程**不能按“Step 12 最终集成完成”处理**。实际应重新定义为：

```text
Step 2~4：主体底座已建立，需要修 Bug 和补强
Step 5：Action 基础较多，但存在严格生存与状态机 Bug
Step 6~7：自主生存/LLM 自主循环尚未形成可靠闭环
Step 8~11：Memory / Skill / Threat / R&D / Building 大量只有骨架，没有正式接入 Runtime
Step 12：尚未达到最终验收前置条件
```

本次修改必须以“**保留现有架构，补齐真实闭环**”为原则。

# 1. 本轮禁止修改的核心架构

以下内容已经符合原策划方向，除修 Bug 外禁止换路线：

1. **真实身体继续是 `EntityMaid`**，禁止换成 Mineflayer、FakePlayer 或第二个玩家实体。
2. **外部 Agent Core 继续使用 Python**，Forge Bridge 只做身体/世界执行。
3. **LLM 不做 Tick 微操**。
4. **Minecraft World 修改只能发生在服务器线程**。
5. **一个 Maid 只有一个 `MotionArbiter`**，其他模块禁止直接 `getNavigation().moveTo()`。
6. **正常生存继续严格禁止 teleport / give / xray / 远程 world edit**。
7. Runtime API 与 R&D API 继续分离；模型名/Base URL 保持用户原样输入。
8. R&D 产物仍只进入 Handoff，**绝不自动写入正式 `mods`**。
9. Control Center 继续作为唯一正常用户入口。
10. 不为了本次修改另建巨大 QA/审计/仿真平台，只增加与真实 Bug 直接相关的最小测试和最终实机验收。

# 6. 第三阶段：修严格生存与 Action 明确 Bug

## 6.1 `UseBlockAction` 禁止直接 `setBlock`

当前类似：


必须删除。

- Maid 必须先在真实交互距离；

- 某些方块无法在不使用 Player 假体的情况下可靠交互时，**宁可返回 `UNSUPPORTED_BLOCK_INTERACTION`，也不直接修改 BlockState 伪装成功**；


# 7. 第四阶段：Action 幂等、抢占和重启恢复

## 7.1 Action 幂等

Agent → Bridge 每个请求至少使用：

```text
session_id
request_id
message_id
```

Bridge 增加近期请求缓存：

```text
request_id -> ACK + final ACTION_RESULT
```

规则：

- 同 request_id 再到达，不重新执行；
- Action 仍运行：重发相同 ACK；
- Action 已结束：重发缓存 Result；
- 缓存按数量/时间淘汰。

涉及：

```text
place_block
break_block
craft
smelt
transfer_container
```

尤其必须防重复执行。

## 7.2 MotionArbiter 抢占回调

现在“高优先级覆盖 Lease”不够。

需要：

```java
MotionPreemptionListener
```

当：

```text
EMERGENCY_REFLEX > TASK
```

发生时：

```text
MotionArbiter
→ ActionEngine.onMotionPreempted(oldActionId)
→ old Action = PREEMPTED
→ ACTION_PREEMPTED EVENT
```

不得让旧 Action 继续认为自己控制导航。

## 7.3 Forge 最小 checkpoint

`MaidAiSavedData` 增加：

```text
protocolVersion
lastSessionId
boundMaid
 autonomyEnabled
lastActionId
lastActionType
lastActionCheckpointJson
```

只保存恢复所需最小数据，不保存巨大状态。

## 7.4 Agent 启动恢复

`MemoryStore` 增加：

```python
load_latest_active_goal()
load_latest_active_plan()
load_strategy_state()
```

启动流程：

```text
HELLO
→ STATE_RESYNC
→ DB 找 ACTIVE/RUNNING Goal/Plan
→ 旧 RUNNING Step = NEEDS_REVALIDATION
→ 根据最新 Snapshot 检查 postcondition
    已满足 → DONE
    未满足且安全 → PENDING/RETRY
    世界改变 → BLOCKED / replanning
```

禁止重启后直接重新执行可能有副作用的旧 Action。

## 7.5 验收

- 放置 Action 请求重复发送两次，只放一个方块；
- 进行 `smelt` 时断 Agent/重连不会重复扣 2 倍原料；
- 战斗反射抢占时旧 Build/Move Action 明确收到 PREEMPTED；
- Agent 重启后能恢复当前 Goal/Plan，而不是从空白人生重新开始。

- 能继续当前已经明确的确定性计划；
- 如果缺乏信息，观察；
- 不具备决策依据时进入 SAFE_IDLE，而不是胡乱探索。

不要求 fallback 代替完整 LLM 长期战略。

## 8.4 生存闭环验收


